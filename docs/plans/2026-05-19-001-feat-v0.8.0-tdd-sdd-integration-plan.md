# feat: v0.8.0 — Spec-then-TDD discipline integration into /athanor:plan + /athanor:work

## Summary

athanor의 `/athanor:plan` Planner A 프롬프트, `/athanor:work` Task Splitter, Executor 디스패처를 강화해서 subtask 단위로 Spec-then-TDD 규율을 자동 적용한다. Splitter가 각 subtask를 `spec-then-tdd | test-aware | direct` 중 하나로 분류하고 behavior-bearing subtask에 MUST/SHOULD acceptance criteria를 박는다. Executor가 분류에 따라 red-first 5단계 / 종료 게이트 / 그대로 분기. 메커니즘은 advisory — Stop hook 같은 runtime 강제는 없고 워커 프롬프트 + 결과 검증으로 운용한다.

---

## Problem Frame

athanor는 정체성으로 "self-sustaining agentic orchestrator"를 표방하지만 현재 워크플로우 어느 단계에서도 test-first 또는 spec-driven 규율을 강제하지 않는다 (skills/plan/SKILL.md, skills/work/SKILL.md grep 결과: TDD/test-first 키워드 0건). 결과적으로 unit별 동작 검증이 worker의 자율 판단에 맡겨지며, v0.7.7 release에서 발견된 M4 escapee나 v0.7.8 PR #16 review에서 발견된 3개 P0 같이 "코드 변경 후 회고적으로 테스트 추가"가 사고 패턴이 됐다. 가시적인 큰 사고는 아직 없지만 가드레일이 없는 상태에서 점점 더 자율적인 워크플로우를 가져가면 부채가 누적된다 (origin: `docs/brainstorms/2026-05-19-001-tdd-sdd-integration-requirements.md` §Problem Frame).

## Requirements

- R1. `/athanor:work` Task Splitter는 plan.md를 분해할 때 각 subtask에 `execution_note` 필드를 추가한다. 값은 `spec-then-tdd | test-aware | direct` 중 하나 (origin R1).
- R2. Splitter는 분류를 자동 결정한다 (user opt-in 아님). 휴리스틱: 소스 코드(.py/.js 등) 수정 + 새 동작/계약 → `spec-then-tdd`; 기존 동작 보존하며 코드 수정 (refactor, 작은 bug fix) → `test-aware`; doc/config/CHANGELOG/`_doc` 등 prose-only → `direct` (origin R2).
- R3. `execution_note: spec-then-tdd` subtask는 `acceptance_criteria` 필드를 갖는다. 값은 MUST/SHOULD로 시작하는 observable assertion 1행 bullets (origin R3).
- R4. `/athanor:work` Executor 디스패치 프롬프트는 subtask의 `execution_note`에 따라 분기한다 — `spec-then-tdd` → red-first 5단계 루프; `test-aware` → unit 종료 게이트 (git diff가 `tests/**` 경로의 어떤 파일이라도 수정 + pytest 통과; `test_*.py`/`conftest.py`/`fixtures/**`/스냅샷/골든 파일 모두 허용); `direct` → 현재 그대로 (origin R4).
- R5. spec-then-tdd subtask에서 worker는 test와 implementation을 같은 step에서 작성하지 않는다 (ce-work 가이드와 동일 원칙, origin R5).
- R6. Worker는 spec-then-tdd subtask의 각 criterion 처리 시 `red_evidence` (실행한 명령, 테스트 노드 id, exit code, output tail)를 ATHANOR_RESULT에 첨부한다. Worker가 어느 criterion에 대해 `red_evidence` 없이 GREEN을 보고하거나 명시적 `red_status: never_red`를 보고하면, Executor 결과 핸들러(leader)가 그 subtask를 `test-aware`로 자동 강등하고 work-log에 사유 기록 (origin R6 — 자동 강등 자체는 leader가 결정하나 RED 발생 사실은 worker의 self-reported evidence에 의존하는 advisory shape임을 명시).
- R7. `execution_note` 필드가 없는 subtask (기존 4개 grandfathered plan-docs 포함)를 worker가 만나면 `direct`로 fallback 처리. work-log에 grandfathered 사유 기록 (origin R7).
- R8. `/athanor:plan` Standard tier 이상의 Critic은 (a) `acceptance_criteria` coverage 적절성과 (b) **behavior 판단의 적절성** — 어떤 phase가 spec-then-tdd 분류가 되어야 하고, 어떤 phase가 test-aware/direct가 되어야 하는지 — 양쪽을 평가 기준에 포함한다. behavior-bearing phase에 MUST/SHOULD가 없거나, 명백한 prose-only phase에 과한 MUST/SHOULD가 있으면 reformulate. Codex 미사용 시 best-effort (origin R8).
- R9. CLAUDE.md `Defense Mechanisms` 표에 본 메커니즘을 advisory로 등재. Stop-Phrase Detection / Read-Before-Edit Rule 와 같은 행으로 (origin R9).
- R10. CHANGELOG.md v0.8.0 항목은 "advisory, planner-classified"임을 명시. "TDD enforced", "Spec-driven required" 같은 과장 표현 금지 (origin R10).

**Origin actors:** A1 (planner agent / `/athanor:plan` Planner A), A2 (executor agent / `/athanor:work` worker), A3 (reviewer agent / `/athanor:plan` Codex critic), A4 (verification skill — 본 작업에선 unchanged), A5 (user/athanor operator)

**Origin flows:** F1 (Standard plan → work 사이클 확장), F2 (work 실행 — spec-then-tdd unit, red-first 5단계), F3 (work 실행 — RED 확인 실패 자동 강등)

**Origin acceptance examples:** AE1 (covers R3, R4 — F2 red-first), AE2 (covers R6 — RED 불가 auto-downgrade), AE3 (covers R7 — grandfathered fallback), AE4 (covers R2 — `_doc` subtask는 `direct`), AE5 (covers R10 — CHANGELOG honesty)

## Key Technical Decisions

- **execution_note + acceptance_criteria의 home은 Subtask 쪽**: Planner A의 Phases는 자유 형식 prose + MUST/SHOULD Verify 필드 유지하고, Task Splitter가 Subtasks 생성 시 분류 + AC 전파. 대안 (Phases-side에 직접 박기)은 Planner A 프롬프트 비대화 위험. Splitter는 이미 prose → 구조화 변환을 수행 중이므로 자연스러운 확장점.
- **버전 bump v0.7.9 → v0.8.0** (minor bump): 새 기능 (advisory discipline) 추가는 의미적으로 minor 변화. v0.7.x 시리즈는 Stop hook 보안 강화 정체성이었으므로 새 정체성 시작은 0.8.0이 적절.
- **test-aware 종료 게이트 strictness (a)**: git diff에 test 파일 (`tests/test_*.py` 패턴) 수정 존재 + pytest 통과만 확인. 새 test 함수 1개 이상 추가 같은 strict 옵션은 false-negative 줄이지만 worker friction 증가. 첫 운용에선 (a) — false-positive 0 우선.
- **3개 분리된 회귀 테스트 파일**: splitter classification, worker dispatch branching, backwards-compat fallback. v0.7.9 패턴 (`test_regression_<area>.py`) 답습. 1개 통합 파일보다 진단 시 명확.
- **Critic은 best-effort AC 검증**: Codex 미사용 환경에서는 critic 자체가 skip되므로 R8은 강제력 없음. plan tier에서 활성화될 때만 발동.

### U3. Executor 디스패치 프롬프트 — execution_note 분기

**Goal:** `/athanor:work` Step 2a의 Executor dispatch packet이 subtask의 `execution_note` 값에 따라 3종류 Ralph-Loop instruction을 분기 적용. spec-then-tdd → red-first 5단계, test-aware → 종료 게이트, direct → 현재 그대로.

**Requirements:** R4, R5

**Dependencies:** U2 (subtask에 `execution_note` 필드 존재 전제)

**Files:**
- Modify: `skills/work/SKILL.md` (Step 2a Build Dispatch Packet, 현재 lines ~273-335)
- Test: `tests/test_regression_work_dispatch_branching.py` (new — **owned by U3+U4 jointly, write FIRST per red-first discipline** before editing the dispatch packet)

**Approach:**

Step 2a의 dispatch packet 빌더에서 prompt 안의 `### Ralph-Loop Instructions` 섹션을 `execution_note` 값에 따라 분기 삽입:

**For execution_note = spec-then-tdd** (Ralph-Loop 대체):
```
### Spec-then-TDD Instructions (execution_note: spec-then-tdd)

You have a list of acceptance_criteria — process each criterion in order:

For each criterion (e.g., "MUST exit 2 when material claim detected"):
1. WRITE: Write a failing test for this criterion in the test file listed under Files.
   Do NOT touch implementation code in this step.
2. RUN: Execute `pytest <test_file>::<new_test_function> -v` via Bash. Capture full output.
3. VERIFY RED: Confirm the test FAILED (exit code non-zero) and record per-criterion red_evidence:
   - command: the exact pytest command run
   - test_node_id: the parametrized test node id (e.g., tests/test_foo.py::test_bar[case-1])
   - exit_code: integer exit code from pytest
   - output_tail: last ~10 lines of pytest output proving the failure mode
   - If the test PASSES on first run, set `red_status: never_red` for this criterion
     in your ATHANOR_RESULT (still record the GREEN-on-first-run command/exit_code as
     red_evidence) and SKIP to the next criterion. The auto-downgrade is handled
     by the leader, not by you.
4. IMPLEMENT: Add the minimum implementation to satisfy this criterion.
5. VERIFY GREEN: Execute the same pytest command. Confirm the test PASSES.
   Also run the full test suite (`pytest tests/`) — all existing tests must still pass.

After all criteria processed:
- Optional refactor pass (improve naming, dedupe — no behavior change)
- Final pytest run — all tests green
- Report ATHANOR_RESULT with per-criterion red_evidence list AND aggregate red_status:
  - `red` if all criteria recorded a RED exit_code != 0 in their red_evidence
  - `partial_never_red` if some criteria had RED but others were never_red
  - `never_red` if all criteria's first-run exit_code was 0 (i.e. tests didn't actually go RED)

The leader will validate that every criterion in your acceptance_criteria list has a
matching red_evidence entry. Missing or malformed red_evidence for any criterion is
treated as `never_red` for that criterion (defensive — workers cannot silently skip the
RED check by omitting evidence).
```

**For execution_note = test-aware** (additional gate appended after current Ralph-Loop):
```
### Test-Aware End Gate (execution_note: test-aware)

You may write tests and implementation in any order. Before reporting success:
1. Run `git diff --name-only` and confirm at least one path is under `tests/` (i.e.
   matches `^tests/.*` regex — this includes test_*.py files, conftest.py, fixture
   modules under tests/fixtures/, snapshot files, golden files, etc.).
   If no path under tests/ has changes, REPORT failure — test-aware subtasks require
   test artifact changes.
2. Run `pytest tests/` — full suite must pass.
3. Report `tests_modified: true` and the list of test artifact paths touched in your
```

**Approach:**

Step 2b의 "If success:" 블록에 신규 분기 추가. 본 핸들러는 worker의 self-reported `red_evidence` + `red_status`에 의존하는 **advisory self-report shape**이다 — leader가 RED 발생을 독립 검증하지는 않지만 evidence의 shape (command, test_node_id, exit_code, output_tail)을 검증해 worker가 형식만 채우고 실제 검증은 안 한 경우를 일부 잡는다:

```
**After worker returns** (success path, before work-log append):

Phase 1 — validate red_evidence shape for spec-then-tdd subtasks:
  For each criterion in subtask.acceptance_criteria:
    Find matching entry in ATHANOR_RESULT.red_evidence.
    If absent OR missing any of {command, test_node_id, exit_code, output_tail}:
      - Mark this criterion as "never_red" (defensive default)
    If exit_code == 0 (RED check passed without failure):
      - Mark this criterion as "never_red"

  If ALL criteria are never_red → red_status_resolved = "never_red"
  If SOME criteria are never_red → red_status_resolved = "partial_never_red"
  Else → red_status_resolved = "red"

Phase 2 — apply downgrade rule (updated post Codex/Opus dual-review):
  If red_status_resolved in {"never_red", "partial_never_red"}:
    - Mark the subtask as downgrade-pending (NOT immediately complete). The
      actual completion decision is deferred to Phase 3 — a downgraded
      subtask must STILL pass the test-aware gate before being marked
      complete. Without this rule, a worker that fabricates red_evidence
      failures (or never writes tests) could be silently marked successful
      via downgrade.
    - Append to work-log.md (pending entry):
      ```
      ## Subtask {id}: pending [auto-downgraded: spec-then-tdd → test-aware, awaiting gate]
      - Reason: red_status_resolved={value}
      - effective_execution_note: test-aware
      - never_red criteria: [list]
      ```
    - No user escalation. Phase 3 then enforces.

Phase 3 — test-aware gate enforcement (applies to original test-aware
subtasks AND Phase-2-downgraded spec-then-tdd subtasks; conjunction of
three signals — all three MUST hold):
  1. ATHANOR_RESULT.tests_modified == true AND test_paths_touched non-empty
  2. ATHANOR_RESULT.full_suite_passed == true (worker self-reports pytest
     tests/ exit code 0; missing field treated as false)
  3. The verification: free-form prose line is consistent with (2)
  If any of the three fails:
    - Mark subtask as failed; increment consecutiveFailures
    - work-log names the specific failing gate clause; if this was a Phase 2
      downgrade, update the pending entry to ✗ failed [downgraded then
      gate-rejected]
  If all three pass:
    - Subtask complete; update pending entry to ✓ {title} [auto-downgraded:
      spec-then-tdd → test-aware]
```

**Honesty arc**: this is advisory self-reporting — a worker can fabricate `red_evidence`

shape) but does not detect adversarial forgery. Runtime hard-enforcement of red_evidence
authenticity (Stop hook style) is deferred to v0.8.1+ verification skill extension.

## Risks & Mitigations

- **Splitter 오분류 (false-positive/false-negative)**: 첫 운용에선 휴리스틱이 정교하지 않을 가능성. *Mitigation*: 사용자가 plan.md를 수동 편집해 execution_note 수정 가능. work-log 기록으로 패턴 사후 분석. v0.8.x에서 휴리스틱 보강.
- **Planner-time 가시성 약화 (subtask-side classification)**: `/athanor:plan` 산출물과 Critic 리뷰는 phase-level의 MUST/SHOULD Verify만 본다 — 최종 subtask label (execution_note)은 Task Splitter (work skill 단계)가 결정하므로 사용자가 plan.md 확인 시점에는 어떤 subtask가 spec-then-tdd로 분류될지 알 수 없다. *Mitigation*: (1) U5 Critic이 phase-level의 분류 가능성을 예측해 misclassification 위험을 미리 표시 (axis B); (2) Splitter 산출 후 plan.md는 사용자가 다시 검토 가능 — `## Subtasks` 블록이 작성된 후 `/athanor:work` 진행 전 break point가 있음 (사용자가 Splitter 출력을 수동 편집할 수 있음); (3) work-log에 실제 분류 결과가 누적되므로 사후 추적 가능.
- **RED 안 가는 case가 너무 잦으면 test-aware로의 자동 강등이 noise**: spec-then-tdd가 사실상 test-aware와 동일하게 동작하는 케이스. *Mitigation*: work-log의 `red_status_resolved` 빈도 데이터로 운용 효과 측정 후 휴리스틱 조정.
- **Worker가 spec-then-tdd 분기를 무시하고 결과만 거짓 보고 (R6 semantics drift)**: 본 메커니즘은 advisory self-report shape — leader가 `red_evidence`의 *shape* (command/test_node_id/exit_code/output_tail)는 검증하지만 *진실성* (worker가 실제로 RED를 본 적 있는지)은 검증 불가. Worker가 단순히 evidence를 fabricate하면 우회 가능. Origin R6 ("work skill detects")이 실제로는 "work skill validates worker's self-report"가 됨을 명시적으로 인정. *Mitigation*: 본 작업에선 advisory로 의도적 한정 (origin §Scope Boundaries — verification skill 확장 = v0.8.1+ 후보). evidence shape 검증으로 가장 흔한 실수 (RED step 건너뛰기) 일부는 잡힘. CHANGELOG honesty 약속 안에 이 한계 명시.
- **기존 4개 grandfathered plan docs의 동작 변화**: 0이어야 함 (R7). *Mitigation*: 신규 회귀 테스트 (test_regression_work_dispatch_branching.py)에 grandfathered fallback 경로 명시.
- **버전 bump 일관성 회귀**: 6개 파일에 v0.8.0 동시 적용 — 누락 시 기존 schema URL 회귀 테스트가 잡음. *Mitigation*: U8 단위 verification으로 강제.
- **CHANGELOG honesty 위반**: "advisory"를 빼고 "enforced"로 적으면 정체성 약속 깨짐. *Mitigation*: U6의 `tests/test_regression_claude_md_honesty.py` 확장으로 negative assertion (`"enforced" not in spec_then_tdd_section`).
- **테스트가 먼저 작성되지 않으면 본 plan 자체가 자기 규율을 위반**: 본 plan의 unit 대다수가 `execution_note: spec-then-tdd`로 표기됨. test 파일을 implementation 다음에 작성하면 RED-first가 깨짐. *Mitigation*: Phased Delivery에서 각 behavior unit이 자기 test 파일 생성을 "sub-step A: write failing test first"로 명시. U7은 honesty 확장 + 총 test 수 검증으로 축소.

## Phased Delivery

각 behavior unit이 자기 test를 **먼저** 작성 (RED 확인) 한 뒤 implementation을 한다 — 본 plan이 자기 규율을 자기에게 적용하는 셈. 작업 묶음 (commit 그룹):

- **Phase A (Planner side, U1 + U5)**:
  1. `tests/test_regression_plan_a_prompt_verify_format.py` 신규 작성 → pytest run → RED 확인
  2. `tests/test_regression_critic_ac_coverage.py` 신규 작성 → pytest run → RED 확인
  3. `skills/plan/SKILL.md` Planner A prompt + Critic prompt 수정
  4. pytest 재실행 → 두 신규 파일 GREEN + 기존 154개 그대로 GREEN
  5. commit: `feat(plan): Verify field as MUST/SHOULD bullets + Critic AC+classification rubric (U1, U5)`
- **Phase B (Worker side, U2 + U3 + U4)**:
  1. `tests/test_regression_splitter_execution_note.py` 신규 작성 → RED 확인
  2. `tests/test_regression_work_dispatch_branching.py` 신규 작성 (U3 + U4 contracts 양쪽 포함) → RED 확인
  3. `skills/work/SKILL.md` Splitter + Dispatch + Result handler 수정
  4. pytest 재실행 → 신규 GREEN + 기존 GREEN
  5. commit: `feat(work): execution_note + acceptance_criteria + red-first dispatch + auto-downgrade (U2, U3, U4)`
- **Phase C (Docs, U6)**:
  1. `tests/test_regression_claude_md_honesty.py` 확장 (신규 row + 서브섹션 검증 함수 추가) → RED 확인 (CLAUDE.md 미수정 상태)
  2. `CLAUDE.md` + `docs/STATE.md` 수정
  3. pytest → GREEN
  4. commit: `docs: Defense Mechanisms row + Spec-then-TDD subsection (U6)`
- **Phase D (Honesty meta, U7)**:
  1. `tests/test_regression_v0_8_0_completeness.py` (선택) 작성 — 메타 검증
  2. claude_md_honesty 확장은 Phase C에 흡수됐으므로 U7은 작은 cleanup
  3. commit: `test: v0.8.0 completeness regression (U7)`
- **Phase E (Release, U8)**:
  1. 6개 파일 버전 bump + schema URL pin
  2. `CHANGELOG.md` v0.8.0 entry prepend
  3. pytest → 기존 schema URL 회귀 + honesty 회귀 모두 GREEN
  4. commit: `chore(release): v0.8.0 — Spec-then-TDD discipline (advisory, planner-classified) (U8)`

각 Phase 종료 시 `pytest tests/` 전체 green 보장. PR 출하 시 5개 commit 단일 squash-merge 또는 개별 보존 (현 athanor 패턴은 squash).
