## Key Technical Decisions

- **KTD1 — Detection mechanism: stdin payload, not filesystem flags.**
  Per the spike timing-race finding (docs/STATE.md §"Command-hook Stop blocking spike (2026-05-18)"), filesystem state is unreliable for gating because of write-commit timing vs hook-fire timing. The script reads stdin (Claude Code injects the Stop event JSON containing `last_assistant_message`) and decides entirely from that payload + the script's own grep over the message body. No `/tmp/` flags. No env vars (except read-only profile lookup from `athanor.json`).

- **KTD2 — Material-claim phrase whitelist: port from v0.7.7 prompt, not reinvent.**
  The v0.7.7 `hooks/hooks.json` Stop prompt has a well-tuned, narrowed material-claim list (edits/tests/releases/migrations/deployments/verification-output + Korean parity: 수정/반영/구현/완료/통과/성공/배포/생성/삭제/수행/적용했습니다 etc.). Port that list verbatim into the Python script's detection function. Same whitelist = same trigger surface = no behavior regression for users between v0.7.7 prompt mode and v0.7.8 command mode (only the enforcement strength changes).

- **KTD3 — Cross-platform invocation: launcher shim, not bare `python3`.**
  Per Codex review and cross-platform observation in the spike, `python3` may not resolve on Windows runners or user installs. Decision: `hooks/hooks.json` invokes a shim script (`scripts/hooks/stop_verify_claims.sh` on Linux/macOS, `scripts/hooks/stop_verify_claims.bat` on Windows OR a single `.py` invoked via shebang with `#!/usr/bin/env python3` and chmod +x). Pick approach during planning bootstrap below.
  - **Picked**: shebang-based single script `scripts/hooks/stop_verify_claims.py` with `#!/usr/bin/env python3` shebang + chmod +x; hooks/hooks.json `command` invokes it via just its absolute repo-relative path. On Windows, GitHub Actions runners and PowerShell users typically have `py.exe` not `python3`, but the GitHub Actions Python setup-action handles this for CI; for end-user Windows installs, document the workaround in CHANGELOG. (Lower risk than scripting a launcher; matches the v0.7.7 spike approach.)

- **KTD4 — `hooks.profile` value: keep `off`+`standard` only (delete or ignore `lenient`/`strict`).**
  Both reviewers (Opus more permissive, Codex stricter) agreed the four-profile ladder is over-engineered for the verified defect. v0.7.8 ships `off` (gate disabled, script exits 0 unconditionally) and `standard` (default; full material-claim detection). Unknown profile values produce a loud stderr warning AND exit 0 (fail-open, not fail-closed — a misconfigured profile should not break stops; it should warn). Codex reviewer recommended fail-closed for safety; we override here because a fail-closed Stop hook bricks the user's session and forces them to manually edit hooks.json, while fail-open just disables a defense (which the user is already opting out of via misconfiguration). Document this trade-off in the script.

- **KTD5 — `hooks.disabled` field: removed in v0.7.8.**
  No code references it. Schema marks deprecated in v0.7.7. v0.7.8 removes the key from athanor.json + templates/athanor.json + schema. Future "disable individual hooks" feature would use a different mechanism.

- **KTD6 — Sentinel format: HTML comment with version tag (`<!-- athanor:verification-emission v=1 -->`), anchored at response start.**
  Per origin §4 M2 design. The hook script matches the sentinel ONLY when it appears as the response's first non-whitespace line (no leading greeting, no leading heading). Trade-off: brittle to model formatting (the verification skill must place the sentinel literally first), but versioned (v=1 lets v0.8.0 evolve to v=2 without backward-incompatible breakage), invisible in rendered Markdown, and namespace-safe (`athanor:` prefix avoids collision with future skills).

- **KTD7 — Replace, don't extend, `tests/test_regression_stop_prompt.py`.**
  That test asserts `type: prompt` and a non-empty prompt field. After R1, the Stop hook is `type: command` with no prompt field; that test will fail. v0.7.8 replaces it with `tests/test_regression_stop_command_hook.py` covering the new contract. The existing test file is deleted; commit message explicitly references the contract change so future archaeology can find why.

- **KTD8 — Housekeeping decision for `fix/plugin-safety-hardening`.**
  This branch (commit b0e30c3 by user wooklae) modifies skills/plan/SKILL.md, skills/setup/SKILL.md (expands embedded fallback), skills/work/SKILL.md, and adds `tests/test_regression_plugin_safety_hardening.py`. v0.7.7 merge did NOT incorporate it. The safety-hardening tests (shell-injection prevention in Codex dispatch prompts) are valuable. Decision: rebase the branch onto current main and convert to a separate PR (v0.7.7.1 patch or v0.7.8 part 0); do NOT delete. The rebase happens as U2 (housekeeping). If conflicts emerge from v0.7.7 changes, evaluate per-conflict; do not auto-resolve.

## High-Level Technical Design

This illustrates the intended approach and is directional guidance for review, not implementation specification. The implementing agent should treat it as context, not code to reproduce.

### Stop hook dispatch flow (v0.7.8)

```mermaid
sequenceDiagram
    participant CC as Claude Code (Stop event)
    participant Hook as scripts/hooks/stop_verify_claims.py
    participant Conf as athanor.json
    participant Model as Active model

    CC->>Hook: stdin payload (JSON with last_assistant_message)
    Hook->>Hook: 1. Parse stdin → extract last_assistant_message
    Hook->>Conf: 2. Read .hooks.profile (jq or json.load)
    alt profile=="off"
        Hook-->>CC: exit 0 (gate disabled)
    end
    Hook->>Hook: 3. Check response prefix for sentinel<br>^<!-- athanor:verification-emission v=
    alt sentinel present
        Hook-->>CC: exit 0 (re-entry skip)
    end
    Hook->>Hook: 4. Grep message body for material-claim phrases
    alt no material claim
        Hook-->>CC: exit 0 (no claim, no gate)
    end
    Hook->>Hook: 5. Verification skill already invoked this turn?<br>(future enhancement — see v0.8.0)
    Hook-->>CC: exit 2 + stderr "athanor: material claim detected;<br>invoke verification-before-completion before stopping"
    CC->>Model: feed stderr as continuation context
    Model->>Model: invoke verification skill →<br>output prefixed with sentinel
    Note over Model,CC: Next Stop event fires
    CC->>Hook: stdin payload (this time sentinel-prefixed)
    Hook-->>CC: exit 0 (sentinel detected, re-entry skip)
```

### Material-claim detection (port from v0.7.7 prompt)

The Python script's detection function should be structured as:

```text
def is_material_claim(message: str) -> bool:
    # Layer 1: English action verbs (past tense + past participle)
    en_verbs = ["created", "deleted", "modified", "removed", "merged",
                "deployed", "released", "fixed", "applied", "tested",
                "verified", "passed", "succeeded"]  # whitelist, not greedy
    # Layer 2: English claim phrases
    en_phrases = ["tests pass", "build succeeded", "lint clean",
                  "files changed", "verification confirmed"]
    # Layer 3: Korean verbs (per v0.7.7 prompt's Korean parity)
    ko_verbs = ["수정", "반영", "구현", "완료", "통과", "성공",
                "배포", "생성", "삭제", "수행", "적용"]
    ko_anchors = ["했습니다", "됐습니다", "완료", "통과", "성공"]
    # All matches must occur in a sentence describing repo/test/build state,
    # not in a quoted-historical-claim ("the v0.7.6 docs said 'tests pass'").
    # For v0.7.8, the implementation may use a simple any-phrase-match heuristic;
    # quoted-attribution detection is v0.8.0+ work (would require sentence parsing).
    ...
```

Directional only — the implementer chooses the exact data structure, whether to use compiled regex or naive `in`-checks, and whether to layer the whitelist in a config file or inline.

### State machine for `hooks.profile`

```text
profile     | gate behavior                                    | unknown→
------------|--------------------------------------------------|------
off         | exit 0 unconditionally                           | n/a
standard    | full material-claim detection (the new default)  | n/a
(missing)   | treat as standard                                | n/a
<other>     | log "unknown profile: <value>" + treat as standard | fail-open
```

## System-Wide Impact

The Stop hook is a cross-cutting defense mechanism. v0.7.8 changes its enforcement model:

| Surface | v0.7.7 behavior | v0.7.8 behavior |
|---|---|---|
| Material-claim turn | Prompt nudges model to invoke verification skill; model decides whether to comply | Hook script exits 2; Claude continues processing with stderr as context; model must invoke verification skill |
| Verification skill output | Output flows back; hook prompt re-fires on it (re-entry risk noted in spike) | Output prefixed with sentinel; hook script detects and exits 0 silently |
| Analysis / planning turn | Prompt skipped via "Explicitly skip" clause | Hook script's `is_material_claim()` returns False; exits 0 |
| User wants to disable | No supported mechanism (orphan profile config) | `athanor.json` `hooks.profile: "off"` honored |

**Risk surface change:** v0.7.7's failure mode was "model rationalizes past advisory prompt" — silent escape. v0.7.8's failure mode is "user's session blocks at Stop because hook script misclassifies non-material claim as material" — loud escape (user sees the stderr feedback). The new failure mode is recoverable (user invokes verification, Stop succeeds) but more disruptive. Mitigation: KTD2's whitelist is the v0.7.7 prompt's already-tuned list, so the trigger surface should not expand.

**Affected stakeholders:**
- End users of athanor — see new Stop-blocking behavior when claiming work without evidence; recoverable but new.
- Codex-based workers — same hook fires on Codex Stop events; the script is model-agnostic.
- Plugin maintainers — new script + new test surface; documented in scripts/hooks/ + tests/.
- CI — same workflows; just `pip install jsonschema pytest` (no new deps).

## Risk Analysis & Mitigation

**Risk 1: False-positive material-claim detection.**
- *Likelihood*: Medium. The v0.7.7 prompt's narrowed whitelist was tuned for v0.7.2 user-fatigue; porting it preserves that tuning. But a real-language sentence ("the tests pass on my machine but not in CI") might trigger over-broadly.
- *Impact*: User sees Stop blocked, must invoke verification skill. Friction but not data loss.
- *Mitigation*: KTD2 — exact port, no expansion. New phrases require a planning cycle to add. Document `hooks.profile=off` as the escape hatch.

**Risk 2: Sentinel placement brittleness.**
- *Likelihood*: Medium. Models may prepend greetings or analysis before the sentinel; anchored-at-start matching then fails.
- *Impact*: Infinite re-entry loop — Stop hook keeps blocking because it doesn't see the sentinel.
- *Mitigation*: U2 instruction at top of verification skill body (before Iron Law). Add a fail-safe: hook script could implement a "same-session-Stop-count" counter (skip exit 2 if this is the Nth consecutive Stop event in the session). Defer counter to v0.8.0 unless real-world testing shows loops.

**Risk 3: Cross-platform `python3` resolution.**
- *Likelihood*: Medium on Windows, low on Linux/macOS.
- *Impact*: Hook fails to invoke on user install; Stop gate silently does nothing (Claude Code logs failure but doesn't propagate to user).
- *Mitigation*: KTD3 — single shebang script. CI matrix includes windows-latest. Document Windows behavior in CHANGELOG. If CI fails, switch to a launcher pre-merge.

**Risk 4: Pre-existing user `hooks.profile=lenient` configurations silently downgrade to standard.**
- *Likelihood*: Low (the v0.7.7 schema marked these deprecated, and the keys were always orphan — no one's config actually had behavior tied to these values).
- *Impact*: User sees no behavior change (lenient was a no-op anyway) + a stderr warning.
- *Mitigation*: CHANGELOG explicit migration note.

**Risk 5: `tests/test_regression_stop_prompt.py` deletion accidentally regresses the Stop-event-presence invariant.**
- *Likelihood*: Low.
- *Impact*: A future "no Stop hook" regression goes uncaught.
- *Mitigation*: U5 — the replacement test `test_regression_stop_command_hook.py` asserts a Stop hook entry exists (just with `type=command` instead of `type=prompt`). Coverage of "Stop event has any registration" is preserved.

## Rollback Plan

If v0.7.8 ships and causes user-visible breakage (e.g., false-positive Stop blocks frustrate users into uninstalling):

1. **Quick rollback (v0.7.8.1 emergency patch)**: keep the command-hook registration but make the script always exit 0 (no-op gate). Users get the new contract but no enforcement, while we investigate the false-positive root cause. This is a 1-line change.

2. **Full rollback (revert v0.7.8 entirely)**: revert the PR; downgrade plugin.json/marketplace.json/$schema URL to v0.7.7. The v0.7.7 advisory prompt-mode hook is well-tuned and known-good.

3. **User-side mitigation while patch is in flight**: tell users to set `"hooks": { "profile": "off" }` in their `athanor.json` to disable the gate immediately. Document in PR description so it's findable from the GitHub release notes.
