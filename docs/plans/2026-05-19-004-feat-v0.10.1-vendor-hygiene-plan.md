# feat: v0.10.1 — Vendor hygiene + Splitter classification_reason

## Summary

athanor v0.10.1 is a small follow-up release that ties up three deferred items
identified during the v0.10.0 absorption and earlier in v0.8.0. No identity
decisions, no architectural shifts — purely hygiene that improves drift
visibility, provenance accuracy, and Splitter auditability. Three concerns:

- **A1 (v0.10.0 §Deferred)**: ship `scripts/check_vendor_drift.py` so the
  manual drift process documented in `docs/STATE.md` §Vendor Manifest becomes
  a single command + CI check.
- **B3 (v0.9.0 follow-up)**: replace the placeholder `source-commit: vendored
  at athanor v0.9.0 release time` in `skills/discuss/references/clarify-gap-
  probes.md` and `skills/discuss/references/requirements-capture.md` with
  immutable upstream commit hashes from the compound-engineering plugin
  cache (v3.8.2 at original vendor time → v3.8.3 verification at v0.10.0
  vendor time).
- **B1 (v0.8.0 Codex Medium #3)**: add `classification_reason` field to the
  Splitter output schema in `/athanor:work` so each subtask's
  `execution_note: spec-then-tdd | test-aware | direct` decision is
  auditable; add 2-3 ambiguous-case fixtures so the classification heuristic
  has explicit unit-test coverage at the edges.

---

## Problem Frame

Three small irritants surfaced from v0.10.0 PR #21 and earlier releases:

1. **Drift visibility (A1):** v0.10.0 ships 267 vendored files from two
   upstream plugins. `docs/STATE.md` documents a manual diff process but
   nobody will run it on a schedule. Without a scripted check, the next
   time someone wonders "is our vendored CE skill still in sync with CE
   v3.8.3?" they have to invent the diff command. This is friction that
   compounds; a 30-line script kills it.
2. **Provenance accuracy (B3):** the v0.9.0 vendored references record
   `source-commit: vendored at athanor v0.9.0 release time` instead of an
   immutable upstream Git commit hash. This was acceptable at v0.9.0 time
   ("we'll fix it in a follow-up") but leaves a small honesty-arc gap —
   the provenance block claims more than it delivers, since "at release
   time" tells the auditor nothing about which exact upstream content
   was vendored.
3. **Splitter auditability (B1):** v0.8.0 Spec-then-TDD discipline relies
   on the Splitter classifying each subtask as `spec-then-tdd | test-aware
   | direct`. Today the classification heuristic is prose in
   `skills/work/SKILL.md` Step 0.5 (Rules block). When a Splitter
   misclassifies, the audit trail is empty — there's no "why did this
   subtask get `direct`?" field on the Splitter's output. The Codex review
   on PR #19 flagged this as Medium #3 and athanor deferred it explicitly
   to v0.8.0.1. v0.10.1 closes the loop.

None of these are user-facing bugs; all three are foundation-tidying work
that would feel ugly to skip but is too small to justify its own release.
Bundling them keeps churn low.

## Key Decisions

- **D1 — Drift check shape.** `scripts/check_vendor_drift.py` iterates
  `skills/ce-*/` and `skills/sp-*/`, locates the matching upstream cache
  directory under `~/.claude/plugins/cache/`, and runs `diff -r`. Reports
  per-skill drift status (`unchanged | content-changed | path-missing`).
  Exit codes: `0` (no drift), `1` (drift detected), `2` (upstream cache
  unreachable). Manual invocation primary; CI invocation prints a
  warning-only summary (does not fail the build — drift is informational,
  not blocking).
- **D2 — SHA-pinning fallback policy.** Some vendored content (e.g.,
  v0.9.0 references) was sourced from a plugin cache that doesn't expose
  upstream Git history. When SHA is unreachable, the corrected
  `source-commit` line records `<plugin>@<version> <relative-path>` —
  the same format v0.10.0 used. Honest framing: "version-tag pin, SHA
  not available from plugin-cache distribution". Document the fallback
  in CLAUDE.md §"Vendored Surface" subsection on drift.
- **D3 — `classification_reason` is a one-line string, not a structured
  object.** Splitter's prompt asks for a single sentence explaining the
  classification ("contains source-code mod + new behavior → spec-then-
  tdd" or "tests/** only, doc-shaped change → direct"). Splitter
  consumer (`/athanor:work` Phase 1 result handler) MUST log
  `classification_reason` alongside `execution_note` to the work log.
  No schema enforcement on the string content; only presence + non-empty
  asserted in regression test. Higher-effort structured reason fields
  (e.g., enum of heuristic triggers) deferred to v0.10.2+.
- **D4 — Ambiguous-case fixtures: 3 cases.** One per classification:
  - spec-then-tdd ambiguity: subtask description that mixes "fix typo"
    (direct shape) with "add new error path" (spec-then-tdd shape) →
    expected classification + expected `classification_reason` excerpt.
  - test-aware ambiguity: subtask that touches code but the change is
    pure refactor → expected `test-aware` + reason.
  - direct ambiguity: subtask that edits prose but the prose is a
    contract document (e.g., AGENTS.md) → expected `direct` + reason
    that surfaces the prose-contract heuristic.
  Each fixture stored as YAML or JSON under `tests/fixtures/splitter_cases/`
  with the input subtask brief + expected classification + expected
  reason-fragment.

## Implementation Units

### U1. Ship `scripts/check_vendor_drift.py` + minimal CI wire-up

**Goal:** A single command (`python3 scripts/check_vendor_drift.py`) that
walks every `skills/ce-*/` and `skills/sp-*/` directory, locates the
matching upstream cache path, and reports drift status.

**Requirements:** D1, A1 (v0.10.0 deferred).

**Dependencies:** none.

**Files:**
- Create: `scripts/check_vendor_drift.py`.

**Approach:** Stdlib only (mirrors `check_release_ready.py` discipline).
For each vendored skill directory, derive upstream candidates: (1)
strip `ce-`/`sp-` prefix, (2) try with prefix preserved (CE's
`/athanor:ce-lfg` was renamed from upstream `lfg`, so for non-prefixed
upstream names try both). Iterate plugin-cache root paths from a known
list (CE under `compound-engineering-plugin`, superpowers under
`claude-plugins-official/superpowers`). For each match, run `diff -r`
through `subprocess.run` and report. Output format: TSV per skill +
end summary; non-zero exit on drift. The script does NOT try to install
or update upstream plugins; if cache is missing, exit 2 with a clear
"install plugin or pass --offline" message.

**Test scenarios:**
- happy: every vendored skill has matching upstream; no diff → exit 0.
- edge: upstream cache missing for one skill → exit 2 with name in
  output.
- edge: one skill has body diff (intentionally inject a test file
  difference) → exit 1 with skill name + first 50 lines of diff.
- edge: vendored skill that was renamed (`ce-lfg` from upstream `lfg`)
  → script resolves the rename and runs diff correctly.

**Verification:** `tests/test_regression_v010_1_vendor_drift_script.py`
covers the four scenarios above.

**Execution note:** Test-first — write the test that asserts the
script's exit-code behavior on a fixture vendored tree, then implement.

### U3. Extend Splitter output schema with `classification_reason`

**Goal:** Each subtask emitted by the `/athanor:work` Splitter (Step 0.5)
carries a `classification_reason: <one-line>` field alongside its
existing `execution_note`. Splitter prompt updated; result handler
logs the field; regression test pins the field's presence.

**Requirements:** D3, B1 (v0.8.0 Codex Medium #3).

**Dependencies:** none.

**Files:**
- Modify: `skills/work/SKILL.md` Step 0.5 §"Rules per subtask" — add
  one-line instruction to emit `classification_reason`.
- Modify: `skills/work/SKILL.md` Step 0.5 §"Output Format" — extend
  the per-subtask block schema with `classification_reason: ...` after
  `execution_note: ...`.
- Modify: `skills/work/SKILL.md` Step 1 (or wherever the Phase 0.5
  result handler is) — when consuming the Splitter's ATHANOR_RESULT
  block, log `classification_reason` to `.athanor/sessions/<id>/work-log.md`
  under each subtask entry.

**Approach:** Pure prose update. The classification heuristic itself
is unchanged (heuristic stays as v0.8.0); only the *recording* of why
the heuristic fired gets added. The reason field is descriptive
("source-code mod + new behavior" / "tests/** only" / "doc-shape edit")
not prescriptive — Splitter still applies the same rules but now
narrates the decision.

**Test scenarios:**
- happy: a 3-subtask plan input to Splitter produces 3 ATHANOR_RESULT
  blocks each containing `classification_reason: <non-empty string>`.
- edge: Splitter output without the field is flagged as malformed by
  the v0.8.0 Phase 1 result handler.
- regression-friendly: SKILL.md §Output Format example shows the new
  field with a realistic value (so future contributors don't have to
  guess the field shape).

**Verification:** `tests/test_regression_splitter_classification_reason.py`
asserts presence + non-empty across the example output blocks in
SKILL.md.

**Execution note:** Test-first. Write the regression test against a
mock Splitter ATHANOR_RESULT first; observe RED on missing field;
then update SKILL.md prose.

| Risk | Severity | Mitigation |
|---|---|---|
| Drift script reports false-positive drift because plugin-cache path differs across machines | Medium | Make plugin-cache root discoverable via env var or `--cache-root` flag; default to common locations + clean error if none found |
